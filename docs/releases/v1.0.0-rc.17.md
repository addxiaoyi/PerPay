# StarPAY 1.0.0-rc.17

Unpublished source candidate. The intended tag `ghcr.io/mashiro0619/perpay:1.0.0-rc.17` has not been published.

Platform fee invoicing now isolates local payment/buyer problems from provider outages. A local failure defers that payment while allowing later candidates to proceed. Provider failures pause the batch with bounded exponential backoff persisted in `system_metadata`, surviving restarts. Uncertain existing applications remain excluded from new issuance. Failed token acquisition is cached for one minute; an explicit readiness probe can refresh it after renewal.

The merchant page shows preparation gates, the latest provider result, and a verified preview of outstanding fees. Administrator-only same-origin/CSRF probes read authorization status while issuance remains off; they never enable invoicing or submit an invoice. Fresh successful probes clear only provider cooldown. Automatic requests recheck the merchant's opt-in after reservation candidates are selected. A configured platform-fee provider rejects new full-payment customer invoice applications while preserving existing-query compatibility.

`scripts/check-fee-invoice-readiness.ts` reads the private profile and SQLite database without opening a writer. With `--check-provider` it reads provider authorization status but never issues invoices or persists diagnostics. Its report includes activation prerequisites and no credentials or buyer identity values.

Database compatibility remains schema 24–72. Migrations 69–72 are unchanged and no migration is added. rc.16 and rc.17 can read the same schema-72 database; a code rollback must retain the current database rather than restoring over newer business records. Preserve a verified database backup and `PERPAY_MASTER_KEY` before deployment. See [fixed-version rollback](https://github.com/Mashiro0619/PerPay/blob/v1.0.0-rc.17/docs/maintenance.md#固定版本与回滚) and [migration recovery](https://github.com/Mashiro0619/PerPay/blob/v1.0.0-rc.17/docs/maintenance.md#数据库迁移备份与恢复).

Real issuance and automatic synchronization remain closed for preparation. Renewed provider authorization is required before platform activation; merchant buyer details are maintained by each merchant and only gate that merchant's invoices. Missing buyer profiles do not block platform activation. Renewal alone does not toggle execution flags. No recharge, real invoice, automatic email or red cancellation is performed by deployment.
