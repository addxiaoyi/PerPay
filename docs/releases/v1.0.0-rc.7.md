# PerPay 1.0.0-rc.7

Merchant owners and administrators can rotate an EPay MD5 key using current
StarMC permissions and a session-bound CSRF token. Rotation requires the expected
key version and a retry ID. The write response contains only version metadata;
the existing reveal control retrieves the new key separately.

Schema 63 retains encrypted key versions and pins a signing version to every
native order. Existing orders continue to sign callback retries and return URLs
with their original key. New order authentication uses the active key. Migration
copies the current encrypted key and associates existing native intents with it;
it does not change payment, balance, ledger or callback records. Key and order
version history cannot be edited or deleted.

Before upgrade, back up the live database with its original `PERPAY_MASTER_KEY`.
Verify the deterministic key-history additions against the exact original key
and order rows; do not merely ignore additional migration tables. Retain the
schema-62 copy and restore it only before new financial records exist. After
admission resumes, rollback must keep the upgraded financial database.

The planned image is `ghcr.io/mashiro0619/perpay:1.0.0-rc.7`; this does not claim
publication. See the [fixed-version recovery procedure](https://github.com/Mashiro0619/PerPay/blob/v1.0.0-rc.7/docs/maintenance.md#固定版本与回滚).
