# PerPay 1.0.0-rc.5

Native merchant refunds use the original verified payment identity. Merchants submit requests; administrators approve them with current StarMC permissions and CSRF protection. Approval freezes the merchant debit, signed provider results settle or release it, and uncertain outcomes keep the hold while a persistent worker queries the same refund number. Original payment evidence and callback ownership remain intact. Refund status is projected into order reads and the merchant console.

Schema 61 adds refund records, attempts and an order-status view. It preserves every existing table. Test coverage must include cross-merchant access, forged administrator fields, partial/full refund limits, duplicate outcomes, lease recovery, signature/amount tampering and transaction rollback. Synthetic transports must never send production refunds.

Legacy `/submit.php`, `/mapi.php` and `/api.php` aliases preserve bodies and query parameters. New invoice requests default to disabled independently of gateway mode (`PERPAY_EPAY_INVOICE_ENABLED=false`), as requested by the operator; historical invoices remain readable.

Before deploying, create a database/key checkpoint and verify restoration under both rc.4 and rc.5. Schema 61 cannot be opened by rc.4. Before traffic admission, rollback may restore the verified pre-upgrade copy; after new financial records exist, preserve them and restore routing by order owner instead of overwriting the database.

This is an unpublished candidate. Its code and isolated tests do not prove production settlement or completed traffic cutover.

Preserve the original `PERPAY_MASTER_KEY` with the verified database backup. The planned image reference is `ghcr.io/mashiro0619/perpay:1.0.0-rc.5`; this does not claim the image has been published. See the [fixed-version recovery procedure](https://github.com/Mashiro0619/PerPay/blob/v1.0.0-rc.5/docs/maintenance.md#固定版本与回滚).
