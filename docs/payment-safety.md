# StarPAY 支付确认与漏通知恢复

只有渠道验签通过、收款账户和应用匹配、系统订单号及渠道交易号一致、金额精确
相符的成功支付，才能改变订单和账本。浏览器跳转、二维码展示、商户传入的状态
或相同金额均不能确认付款。

## 已实施的保护

- 下单身份、商户订单号和原始请求绑定；重试复用原订单，改金额或跨商户复用会被拒绝。
- 渠道请求发出前持久保存订单及请求占用；网络结果不确定时先查单，不重复收款请求。
- 支付证明、订单状态、扣费后入账和回调任务在同一事务提交。重复通知或查单只入账一次。
- 渠道未通知时由持久查单任务补偿。进程重启后按租约恢复，旧进程不能覆盖新任务结果。
- 二维码或页面过期不等于未收款；关单需要渠道验签证据，关单前后均核对支付状态。
- 商户回调持久记录尝试与结果，超时重试；回调失败不会撤销已确认收款或重复入账。

## 商户成功回执

EPay 通知使用 HTTP 2xx 和正文 `success`。
主站兼容通知接受 HTTP 2xx 加正文 `success`，或 JSON `{"ok":true}` / `{"success":true}`。
JSON 字段必须为布尔值，不能包含相反的成功标记或非空错误。
空正文、空 JSON、登录页、`{"ok":false}`、`{"success":false}` 均继续重试。
收到通知的业务方应在持久保存业务结果之后回复成功，并按订单号或幂等键防止重复发货。
HTTP 成功本身不能证明商品或余额已在商户侧到账。

## 接单与监控

下单入口与就绪检查使用同一条件；查单、回调或退款任务未启动时不接新订单。
待确认订单超过两分钟未进入查单、查单期限超过两分钟仍未推进、连续失败五分钟，
或任务状态损坏时，暂停新接单并报告恢复延迟。恢复任务和已有订单回调继续运行，
恢复正常后自动允许新订单。

一致性监控逐商户核对余额、支付证明、账本、通知及查单进度。通知重试耗尽或延迟
会明确报错并保留记录；管理员可在排除接收端故障后重试，不能把“已入队”当作已送达。

## 回归与边界

`npm run test:payments` 已接入 CI，覆盖伪造签名、金额/商户不符、同额订单隔离、
重复通知、事务回滚、漏通知查单、重启恢复、过期关单和错误成功回执。
测试使用合成交易和隔离数据库，不发起真实付款、退款或生产余额调整。

生产验收还需对照官方查单、网关订单、账本和商户回执。历史迁移记录保持原处理方，
归属不明的订单不自动分配。外部渠道或商户不可用时，系统保留待核对与失败记录并
暂停有风险的新接单；不能承诺任何外部故障下都即时完成收款或发货。
