# 支付确认与漏单恢复

rc.22 加强渠道查单、商户回调和重启恢复。目标是让暂时超时留下可继续处理的任务，并确保补偿不会重复入账。不能把浏览器跳转成功或单次 HTTP 200 当作完整支付成功。

## 支付如何确认

订单先持久化，再请求渠道。支付宝和微信的支付通知必须通过签名、商户账户、订单号及金额校验；确认、余额账本和商户通知任务在同一事务中提交。若事务失败，渠道收到失败响应后可以重试，本站也保留查单恢复。

未确定结果的订单由官方查单任务恢复。每轮最多处理 20 笔，最多并发 3 笔；超时或渠道错误不会被当作支付成功。进程重启后，持久化任务租约过期即可重新领取，旧进程的迟到结果不能覆盖新任务。单条任务状态损坏会告警并保持新单受理保护，其他健康订单仍可继续查单。

服务启动先开放 HTTP 回调入口，再恢复积压任务。上游慢响应不再让本站因等待首轮恢复而一直无法接收通知。源数据同步每轮失败后最多再尝试两次，间隔 1 秒、3 秒；每次重新抓取并验签，保持原来的 90 秒新鲜度限制。

## 商户回调如何补发

回调仅在已确认支付和账本一致后发送。商户暂时不可用时，间隔从 30 秒递增至最多 1 小时，每阶段最多 80 次，正常调度下覆盖至少 72 小时。下一次重试时间保存在数据库，重启不清空；不是每秒重打。遇到明确不支持 POST 的 405/415 响应，保留签名 GET 兼容路径并在三次 POST 后切换。

只有约定的成功应答才完成通知。超过重试预算或遇到不可重试配置错误会保留失败记录及人工重试入口，不删除支付记录。监控分别展示“正在等待商户恢复”和“已经超过计划重试时间”，后者以及耗尽失败继续告警。

接入网站必须在自己的数据库事务中完成幂等入账/发货后再返回成功，并以 PerPay 订单号建立唯一约束。重复通知只返回已有结果，不能重复加余额或发货；回调未到时可由网站后台使用签名查询接口核实。浏览器返回页不能触发可信入账。

## 运维判断

按三个独立证据核对：渠道官方支付状态、PerPay 确认与账本、商户业务入账。回调成功代表商户返回了成功应答，不能替代接入网站自身的入账审计。

发现积压时先只读查单，不按相同金额猜测订单、不强制改 PAID、不重放未验签数据。确认渠道已支付但本站未记账时使用原订单的恢复流程；确认本站已支付但商户未入账时使用原通知的重试流程。服务重启与发布保留当前数据库、密钥和任务队列，回滚只切代码，避免用旧备份覆盖新交易。

真实开票开关继续关闭。本次测试全部使用隔离订单和模拟商户响应，没有真实扣款、充值、退款或发票。
