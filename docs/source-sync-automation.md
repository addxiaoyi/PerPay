# 源同步诊断与连续验收

同步仍使用原来的只读 MySQL 抓取、10 秒共享读锁窗口、5 秒主站签名快照窗口、30 秒投递时效和 90 秒新单新鲜度保护。没有用延长时效、跳过验签或减少账务核对来消除超时。

## 已确认的慢阶段

2026-11-25 的一次只读抓取（未调用 apply）耗时 5013ms：MySQL 11 张表读取合计约 213ms，主站签名快照 4331ms，共享读锁保持 4558ms。Order 560 行读取 13ms；同一主站端点此前三个样本分别 46/57/115ms。该证据说明存在主站快照间歇延迟，不能据此把原因归为源表规模。CPU/交换及主站持久化的根因需要结合时间对齐的进程 I/O 证据，不能由单次快照推断。

本次只读冷导入诊断还观测到完整数据库模块导入约 366ms。`--running` 收集进程仅需要读取 instance_id，因此数据库迁移和财务写入模块改为仅离线模式动态载入；快照封包独立于 HTTP 路由依赖图。每次完整抓取结束后立即关闭源连接，异常分支直接销毁连接，避免重试等待挂起查询后的 QUIT。

后续 30 个签名 GET 与 worker I/O 时间对齐：一次 4107ms 慢请求期间，写盘增加 114,925,568 字节（约 109.6MiB），store inode 和 mtime 同时更新，major faults 增加 3081；另一次 1225ms 请求同样对应整文件发布。末尾两次约 6 秒超时期间无写盘进展，但 major faults 分别增加 5399、7226。证据支持主站同步持久化阻塞叠加换页压力；CLI 冷导入改进不能替代主站持久化修复。完整记录为 `artifacts/source-sync-automation-20261125/correlation.log`。

## 日志

成功、重试、最终失败均保留现有事件与 phase 字段，并增加：

- `startupMilliseconds`：本次 CLI 进程启动至入口所用时间。
- `attemptMilliseconds` / `phaseMilliseconds`：本次尝试总时间，以及连接、权限、每张表、签名主站快照、封包和投递耗时。嵌套阶段包含子阶段，不能相加当作总时长。
- `failedStep` / `reason`：最内层失败位置和固定错误分类；不输出异常原文、SQL、快照、密钥或连接配置。
- `ownerPhaseMilliseconds`：新 owner 返回的 `Server-Timing`，区分服务端校验和财务应用耗时；旧 owner 不返回此头时仍兼容。客户端超时而未收到响应时没有这组数值，不能将缺值解释为服务端执行时间为零。

503 的 `apply_rejected` 表示 owner 明确拒绝应用；403 的 `delivery_rejected` 表示投递校验不通过；`request_timeout` 是请求到期。它们不应合并解释为数据库锁超时。

## 有界连续验收

在实际服务器运行，只读取原有状态和系统日志，不启动新同步、不触发支付、退款、充值或订单修改：

```bash
python3 scripts/observe-source-sync.py \
  --data-root /var/lib/perpay-candidate-20261123b \
  --duration-seconds 120 --interval-seconds 10
```

运行窗口限定 30–1800 秒，间隔 5–60 秒。每次仅做一个 readiness GET 和只读同步元数据/游标查询。最终一行 `source_sync_acceptance` 给出样本、成功同步次数、重试/失败次数、慢阶段上限及是否通过。窗口中任一不就绪、源状态不新鲜、日志不可读、没有完成一次同步、发生重试或最终失败，均退出 1；只有全部符合才退出 0。观察结束后的单次健康恢复不能覆盖窗口内失败。

这份结果只证明给定窗口，不能证明长期可用性；账本一致、官方支付确认和商户实际入账仍需独立核对。诊断工件位于 `artifacts/source-sync-automation-20261125/`，其中抓取脚本仅抓取、不会提交候选 delta。
